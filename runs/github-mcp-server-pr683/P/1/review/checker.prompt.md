0. pkg/pagination.go:31: WithUnifiedPagination is not used by any tool, only by pagination_test.go. It also copies the "page", "perPage" and "after" definitions that WithPagination and WithCursorPagination already have, so the same schema text exists in three places. Fix: Delete WithUnifiedPagination and its test case. Then pull the parameter definitions into private options (pageOption, perPageOption, afterOption) and build WithPagination and WithCursorPagination from them.
1. pkg/pagination.go:71: PaginationParams gained an After field and a ToGraphQLParams method. No REST tool reads them, and the GraphQL tools use CursorPaginationParams instead. OptionalPaginationParams now also reads and type-checks "after" on every REST tool, so a REST tool can fail on a parameter its schema does not declare. Fix: Remove After and PaginationParams.ToGraphQLParams. Remove the "after" lookup from OptionalPaginationParams so it only reads page and perPage. Keep cursor handling only in CursorPaginationParams/OptionalCursorPaginationParams, and drop the matching test cases.
2. pkg/pagination.go:94: OptionalPaginationParams hardcodes a default perPage of 30. The new DefaultGraphQLPageSize const (also 30) sits in graphql.go, so the package now keeps two separate sources for the same default. Fix: Add one DefaultPageSize const in pagination.go and use it in both OptionalPaginationParams and OptionalCursorPaginationParams. Delete graphql.go, or keep in it only GraphQL-specific helpers (see the next finding).
3. pkg/discussions.go:412: discussionsPageInfo/toMap and discussionsPaginationVars are general GraphQL connection helpers, but they carry discussion names and live in discussions.go. graphql.go was added as the place for GraphQL helpers and holds only a const. The helper also goes through GraphQLPaginationParams (*int32/*string) only to turn the values straight back into githubv4 types. Fix: Move them to graphql.go as graphQLPageInfo and cursorPaginationVars(request) (the latter could also be a method on CursorPaginationParams). Have them return githubv4.Int/*githubv4.String directly, and remove GraphQLPaginationParams if nothing else uses it.
4. pkg/sub_issue.go:93: The new list_sub_issues tool declares its own "page" and "per_page" parameters (no min/max) and reads them by hand. Every other paginated tool uses WithPagination() with "perPage", so this tool's schema and validation don't match the rest of the package. Fix: Use WithPagination() in the tool definition and OptionalPaginationParams(request) in the handler. Rename per_page to perPage in sub_issue_test.go and update the toolsnap.
5. pkg/sub_issue_test.go:441: The new test helpers repeat helpers that already exist. subIssueClientFn is stubGetClientFromHTTPFn (server_test.go). subIssueHandler and subIssueQueryHandler are expectRequestBody/expectQueryParams(...).andThen(mockResponse(...)) Fix: Replace subIssueClientFn with stubGetClientFromHTTPFn. Replace subIssueHandler/subIssueQueryHandler with expectRequestBody/expectQueryParams(t, ...).andThen(mockResponse(t, status, body)). In callSubIssueTool, use createMCPRequest and getTextResult/getErrorResult, or remove it.
6. pkg/repositories.go:142: ListCommits sets perPage to 30 when it is 0. That can never happen, because OptionalPaginationParams already defaults perPage to 30, so this is dead code that repeats the default. Fix: Delete the perPage local and the if block, and use pagination.PerPage directly in CommitsListOptions.
7. pkg/issues.go:410: ListIssues declares WithPagination() but reads "page" and "perPage" by type-asserting request.GetArguments().
