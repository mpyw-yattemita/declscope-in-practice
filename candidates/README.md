# 候補の探し方と結果

課題の候補（同じ package に続けてマージされた PR の連続）を、どういう要件で、どう探し、何が見つかったかの記録。条件の正式な定義は [design.md](../design.md) の「課題」にある。ここには、それを実際の検索にどう落とし込んだかを書く。

| ファイル | 中身 |
| --- | --- |
| [round2-chains/chains.md](round2-chains/chains.md) | 2回目（連続）の結果。ランク付きの表、各段の詳細、落とした連続 |
| [round2-chains/chains.json](round2-chains/chains.json) | 同じ内容の機械可読版。seed とマージ commit の SHA を含む |
| [round1-pairs/](round1-pairs/) | 1回目（PR のペア）の結果。設計を変えたので使わないが、経緯として残す |
| [survey/](survey/) | 各リポジトリの `declscope survey -format=json` の生の出力 |

## 検索の要件

### package

| 要件 | 検索での判定 |
| --- | --- |
| declscope を使っていない | `.declscope.yaml` がないリポジトリだけを対象にする |
| テスト以外のファイルが 8個以上 | seed の commit で数える |
| namespace が 3つ以上 | `declscope survey` で数える。ただし各リポジトリの HEAD で測った値 |

### 連続の各段（PR）

| 要件 | 検索での判定 |
| --- | --- |
| マージされた PR である | first-parent の履歴で、PR のマージ commit を拾う。2025-01-01 以降 |
| 機能追加か挙動の変更である | タイトルが lint、bump、chore、docs、refactor、rename、flaky test、CI のものは除く。最後は人が読んで判断する |
| テストを伴う | その package のテストファイルを変更している |
| 小さすぎない | package の中のテスト以外の変更が 10行以上 |

### 連続全体

| 要件 | 検索での判定 |
| --- | --- |
| 3〜5本 | ― |
| 規模 | package の中のテスト以外の変更が合計 450〜2600行で探し、600〜2000行を優先する。4ファイル以上 |
| 変更の大半が package の中にある | 連続全体の行数の 45% 以上が package の中 |
| 後の段が前の段のコードを使う | 後の段が、前の段の触ったファイルを触る。さらに、前の段で追加された名前を後の段のコードかテストが使う |
| 連続している | 連続の PR のあいだに、その package を変更した別の commit がない。テストを含めて 20行以下の commit だけは挟まってもよく、記録する |
| テストが upstream の内部の名前に頼りすぎない | 各段のテストが使う名前のうち、連続の中の PR が追加したものを数える。少ないほど良い |
| オフラインでテストが通る | seed と各段のマージ commit で `go test` を実行する |
| 題材として良い | 置き場所の判断が実際に起きるかを、人が読んで判断する。PR ごとに新しいファイルを1つ足すだけの連続は弱い |
| マージ日 | 2026年7月以降を優先する。ただし同じくらい良い候補を比べるときだけ使う |

### テストの実行環境

| 項目 | 値 |
| --- | --- |
| コマンド | `go test -count=1 ./<pkg>` |
| ネットワーク | `sandbox-exec` で、localhost 以外への外向きの接続を遮断。`GOPROXY=off` |
| ツールチェーン | Go 1.27.0、darwin/arm64、`CGO_ENABLED=0` |

`CGO_ENABLED=0` にしたのは、手元の C のリンカが壊れていたため。本番のハーネスでも同じ設定にするか、Linux で確かめ直す。

## 経過

| 回 | 探したもの | 結果 | 次にしたこと |
| --- | --- | --- | --- |
| 1回目 | PR のペア（PR1 と次の PR2） | 14 リポジトリから 19 ペア | PR が小さすぎた（上位でも 100行・2ファイル程度）。次の PR も、PR1 と無関係な小さな修正が多かった。そこで連続に切り替えた |
| 2回目 | 3〜5本の連続 | 7 リポジトリから 9本 | いまここ |

### 2回目の検索の量

| 段階 | 数 |
| --- | --- |
| `survey` を実行した module | 61 |
| package の要件を満たした package | 372 |
| 連続の窓が1つ以上あった package | 88（窓は合計 1,001） |
| 「後の段が前の段のコードを使う」と「45% 以上が package の中」で残った窓 | 539 |
| 名前の数の確認まで通った窓 | 53 |
| 人が読んだ窓 | 約30 |
| 残した連続 | 9 |

### 多く落とした要件

| 要件 | 内容 |
| --- | --- |
| 連続していること | 372 package のうち、要件を満たす PR が3本以上続くのは 88 だけ。途中にテストのない修正、リファクタリング、20行を超える lint の commit が挟まることが多い |
| テストが使う名前 | 539 窓のうち 358 は、連続の中の PR が追加した unexported な名前を5個以上テストで使っていた。prometheus、jaeger、ollama、temporal、quic-go、mcp-go の大半がこれで落ちた |
| 後の段が前の段のコードを使うこと | 173 窓は、後の段が前の段で追加した名前を使っていなかった |
| 機能追加であること | 修正や移行ばかりの連続が多かった（prometheus の discovery/aws、opa の ast、pebble、restic など） |
| ツールチェーン | pebble は Go 1.27 でビルドできなかった。go-git はテストにネットワークが要る |

## 検索で分かった要件の問題

| 問題 | 内容 | 扱い |
| --- | --- | --- |
| 「前の段のコードを使う」と「テストが内部の名前に頼らない」がぶつかる | 後の段が前の段のコードを使うほど、テストもそのコードを直接呼ぶ | **解決済み**。隠しテストの名前をエージェントのコードに合わせる役を置いた（design.md の「隠しテストの名前合わせ」） |
| export された名前を数えると、件数が膨らむ | 構造体のフィールドも数えるので、外部 API を写した package（slack、github-mcp-server）が不利になる | 名前合わせを入れたので、件数そのものは選ぶ基準にしない。「対応なし」が多くなりそうかどうかで判断する |
| 連続の厳しさ | 良い機能追加の連続でも、途中にテスト付きの小さな修正が挟まることが多い | **未決**。テスト付きの小さな修正を、連続の1段として認めるか |
| スナップショットのファイル | github-mcp-server と traefik は、テストが比べるスナップショットやフィクスチャのファイルを課題と一緒に渡す必要がある。ツールのスキーマや説明文を前もって決めてしまう | **未決** |
| package の外の変更 | lazygit は、連続の変更の大半が package の外にある | 45% 以上が package の中、という要件で絞った。lazygit は弱い候補として残した |

## 確かめていないこと

| 項目 | 内容 |
| --- | --- |
| namespace の数 | 各リポジトリの HEAD で測った値。seed の commit では測っていない |
| テストが使う名前 | 追加されたテストの行を、名前のトークンで照合しただけ。package の外にあるテストは見ていない。export された名前は一行ずつ読んでいない |
| 「前の段のコードを使う」 | 名前のトークンで判定した近似 |
| 挟まった小さな commit | 大きさとタイトルで判断した。差分は読んでいない |
| 実行環境 | macOS でだけ確かめた。Linux では確かめていない |
| nats-server | テストを実行していない |
