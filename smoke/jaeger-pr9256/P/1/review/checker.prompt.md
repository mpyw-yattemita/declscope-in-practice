0. pkg/search_capabilities.go:29: `Filter` is a `*FilterCapabilities`, but the zero value of `FilterCapabilities` already means "declares nothing". The pointer adds a second way to say nothing. It also forces the receivers to differ: `IsEmpty` has a pointer receiver because it must handle nil, while `SupportsLevel` and `SupportsOperator` have value receivers. So a caller who writes `caps.Filter.SupportsOperator(op)` on a Reader that left `Filter` nil gets a nil-pointer panic. Only `IsEmpty` is safe to call, and that is why the doc comments have to tell callers to use `IsEmpty` instead of comparing against nil. Fix: Change the field to `Filter FilterCapabilities`, a value. Give `IsEmpty` a value receiver: `func (c FilterCapabilities) IsEmpty() bool { return len(c.Levels) == 0 && len(c.Operators) == 0 }`. Remove the sentences "Callers ask Filter.IsEmpty rather than comparing against nil" here and "Callers ask IsEmpty rather than comparing against nil" in filter.go:28. Update the tests: remove the nil case in filter_test.go and use `FilterCapabilities{}` values. If you keep the pointer instead, make all three methods pointer receivers and have each one return false or true for nil, so no method can panic.
1. pkg/reader.go:48: The `FindTraces` doc still says it is an implementation-dependent ambiguity whether query filters must match within the same span. The new `SearchCapabilities.SameSpanConjunction` now declares exactly that, so the comment is stale. The Reader docs also never mention `TraceQueryParams.Filter`, `ErrFilterUnsupported` or `ErrFilterInvalid`. An implementer has no contract for what to return when it gets a `Filter` it cannot serve. Fix: Replace the ambiguity paragraph with: "Whether a conjunction must be satisfied by a single span is declared by SearchCapabilities.SameSpanConjunction. If query.Filter uses a level, operator or structure outside SearchCapabilities.Filter, the iterator yields an error wrapping ErrFilterUnsupported. If a filter value does not fit its field, it yields an error wrapping ErrFilterInvalid." Let `FindTraceIDs` and `FindTraceSummaries` refer to this paragraph, the way they already refer to the chunking rules.
2. pkg/reader.go:89: Adding `SearchCapabilities` to the `Reader` interface breaks every existing Reader and decorator at once. The package already has a pattern for this case: `UnsupportedTraceSummaries` is embedded so a backend gets the default behaviour of `FindTraceSummaries` without writing it. No such default exists for `SearchCapabilities`, so each backend has to write the same "return SearchCapabilities{}, nil" or the same `ErrUnsupported` stub by hand. Fix: Add an embeddable `UnsupportedSearchCapabilities struct{}` next to `SearchCapabilities` in search_capabilities.go, following the summary.go pattern. Its method is `SearchCapabilities(context.Context) (SearchCapabilities, error)` and returns `SearchCapabilities{}` together with `fmt.Errorf("...: %w", errors.ErrUnsupported)`. Mention it in the Reader doc comment the same way `UnsupportedTraceSummaries` is mentioned. Add a test like `TestUnsupportedTraceSummaries_FindTraceSummaries`.
3. pkg/reader.go:117: The doc says `Filter` is mutually exclusive with `ServiceName`, `OperationName`, `Attributes` and the duration bounds. Nothing in the package enforces this, so every backend has to check it itself, or not check it, and the checks will drift apart. The comment also does not say what happens on a violation. Fix: Add `func (p TraceQueryParams) validateFilterExclusive() error`, or an exported `Validate`, in reader.go. Also update the `ErrFilterInvalid` doc in filter.go:19, which today covers only values that do not fit their field, so it includes this case.
