# 実験2の報告（暫定）

> [!NOTE]
> **暫定の結果。** 分割の良さは AI の判定役だけで判定した。同僚による人の判定はまだ。4課題（jaeger、hcl、traefik、github-mcp-server）を、各群1回ずつ実行した。

## 結論

**分割の良さを一番左右したのは、リファクタリングを頼むかどうかだった。** declscope は、ルールを守らせることには確実に効いた。判定役の見る「分割の良さ」への効き方は、使い方で向きが分かれた。

| 問い | 答え |
| --- | --- |
| リファクタリングさせるとき、declscope は役に立つか（主な比較、R′ 対 R） | **役に立たなかった。** 判定が付いた2課題（traefik、github-mcp-server）では、どちらも declscope のない R が勝った。残る2課題は引き分け |
| 最小限の対応のとき、declscope は役に立つか（M′ 対 M） | **少し役に立った。** 判定が付いた2課題（jaeger、github-mcp-server）では、どちらも M′ が勝った。残る2課題は引き分け。段階2の手間も M′ のほうが少なかった |
| リファクタリングを頼むと、分割は良くなるか（R 対 M、R′ 対 M′） | **はっきり良くなる。** declscope のあり・なしにかかわらず、4課題すべてでリファクタリングを頼んだ群が勝った |
| declscope の群はルールを守ったか | 守った。段階1の終わりに declscope が報告するものは、M′ と R′ では4課題すべてで 0 件。M と R では、すべての課題で残った |

R′ が R に負けた2課題では、どちらも R のほうが大きな塊を切り出した。R は、膨らんだファイルから関連する処理をまとめて別のファイルに移した。R′ は、既存の配置に近いまま進めた（下の表）。declscope の skill は、頼まれた範囲の外では既存の流儀を保つよう求め、範囲の中の変更でも戻ってきた指摘を直すよう求める。その分、R′ は組み直しに慎重になったと読める。一方で、R の組み直しは declscope のルールからは最も離れた（「ルールが守られたか」）。

### R′ が組み直しを控えた理由

R′ にだけ、既存の宣言を動かしにくくする重りがかかっていた。

| 重り | 中身 |
| --- | --- |
| baseline のキー | 既存の宣言を別のファイルに移すか名前を変えると、キーが変わり、記録済みの指摘が戻ってくる。それを直す手間が R′ にだけかかる |
| 命名のルールが export された名前にも効く（`exported: true`） | `RequiredParam` を `params.go` に移すと、`params` を含まないので新しい指摘になる |
| 「export された API を変えない」という範囲の段落 | 上の指摘を、名前を変えて直すことができない。R にとっては、この指示は何の制約にもならない |

トランスクリプトにも、これが出ている。traefik の2段目で、R′ は `kubernetes.go` の `getTLSCert` を新しいファイルから使うのに、移さず `//declscope:shared` を付けた。理由として「名前を変えると、記録済みの baseline の指摘が戻ってくる」と書いている。github-mcp-server では、新しく足したページ送りの処理は `pagination.go` に分けたが、既存の `RequiredParam` などは `server.go` に残し、動かすことを検討した形跡もない。

`//declscope:namespace param` を付けたファイルに移せば、`RequiredParam` は名前を変えずに済む。エージェントはそこまで踏み込まなかった。

**読み方:** これは「baseline のある既存のコードで、export された API を保ったままリファクタリングさせると、declscope は組み直しを控えさせる」という結果でもある。同じ条件なら、実際の現場でも起きる。一方で、「export された API を変えない」が R′ にだけ効く条件だったことは、主な比較の限界になる（「限界」）。

## 課題ごとの結果

| 課題 | R′ 対 R（主） | M′ 対 M | R 対 M | R′ 対 M′ |
| --- | --- | --- | --- | --- |
| jaeger-pr9256 | 引き分け | **M′** | **R** | **R′** |
| hcl-pr841 | 引き分け | 引き分け | **R** | **R′** |
| traefik-pr14130 | **R** | 引き分け | **R** | **R′** |
| github-mcp-server-pr683 | **R** | **M′** | **R** | **R′** |

判定役が何を見たか:

| 課題・組 | 判定役の理由 |
| --- | --- |
| jaeger、M′ 対 M | M は新しい機能をすべて `reader.go` に足し、147行から220行に増やした。M′ はパッケージの既存の分け方（`summary.go`）にならい、`filter.go` と `search_capabilities.go` に分けた |
| github-mcp-server、M′ 対 M | M′ はカーソルによるページ送りを `pagination.go` に、サブ issue のツールを `sub_issue.go` にまとめた。M は、それぞれ `server.go` と、1227行ある `issues.go` に足した |
| traefik、R′ 対 R | R は Gateway の TLS の処理を `gatewaytls.go` に集めた。R′ はその一部を、2321行ある `kubernetes.go` に残した |
| github-mcp-server、R′ 対 R | R は引数を読む補助関数（`RequiredParam`、`OptionalParam` など）を `server.go` から `params.go` に移した。R′ はそれを `server.go` に残した |
| jaeger、R′ 対 R | R は既存の型まで `query.go` に移した。R′ は既存の配置に手を付けなかった。判定役は、順番によって両方を選んだ |
| hcl、R′ 対 R | R′ はトークンを分ける処理を `partition.go` に切り出した。R は入れ子の式ごとに小さな interface を実装させた。判定役は2回とも先に見せたほうを選んだ |
| traefik、R 対 M と R′ 対 M′ | リファクタリングを頼んだ群は、BackendTLSPolicy の処理を `backendtlspolicy.go` にまとめ、HTTP、GRPC、TLS の経路で共有した。最小限の群は、約100行の同じ処理を3つのファイルに写した |

## ルールが守られたか

どの群にも M′ と R′ と同じ設定と seed の baseline を当てて、段階1の終わりのコードに `declscope` と `declscope shrink` を実行した（`analysis/compliance.py`）。

| 課題 | M | M′ | R | R′ |
| --- | --- | --- | --- | --- |
| jaeger | 命名 4 | **0** | 命名 3 | **0** |
| hcl | 境界 14、命名 15 | **0** | 境界 17、命名 30 | **0** |
| traefik | 命名 5 | **0** | 境界 15、命名 16 | **0** |
| github-mcp-server | 境界 1、命名 26 | **0** | 境界 6、命名 34 | **0** |

**declscope なしでリファクタリングさせると、ルールから最も離れた。** R はファイルを分けて組み直すので、ファイルをまたぐ参照が増え、名前もファイルの語を含まなくなる。判定役はそれを良い分割と見たが、declscope の言う置き場所のルールとは別物になった。

## declscope の検査は役に立ったか

M′ と R′ の段階1の各段で、エージェントが実行した `declscope` の出力をトランスクリプトから読んだ（`analysis/guardrail_use.py`）。「役に立った」は、検査が指摘を出し、そのあとの検査で指摘がなくなった段。

| 群 | 役に立った | 指摘が残った | 指摘なし | 実行しなかった |
| --- | --- | --- | --- | --- |
| M′ | 5 | 0 | 8 | 0 |
| R′ | 6 | 0 | 7 | 0 |

エージェントはすべての段で検査を実行し、指摘が出た段ではすべて直した。指摘は、各課題の2段目以降に集中した。

**その代わり、段階1の手間が増えた。** 段階2（あとの変更）の手間は、最小限の対応では declscope のある群のほうが少なかった。

| 群 | 段階1のトークン（4課題の合計） | 段階2のトークン（4課題の合計） |
| --- | --- | --- |
| M | 1543万 | 664万 |
| M′ | 2305万 | 570万 |
| R | 2538万 | 621万 |
| R′ | 3144万 | 688万 |

段階2のトークン比（課題ごとの比の平均と 95% 区間）は、M′ 対 M が 0.85（0.69〜0.96）で、区間が 1 を下回った。M′ が残したコードは、次の変更が少ない手間で済んだ。R′ 対 R は 1.10（0.95〜1.21）で、差は見えない。

## 判定ルールの結果

`analysis/analyze.py` が [design.md](design.md#判定ルール) のルールで出した結果。詳細は [analysis/results.md](analysis/results.md) にある。

| 比較 | 歯止め | 分割の勝率 | 判定が付いた課題 | 結果 |
| --- | --- | --- | --- | --- |
| 主: R′ 対 R | 下がっていない（R′ 1 / R 2） | 0.00 | 2 / 4 | R の勝ち |
| 副: M′ 対 M | 下がっていない（M′ 1 / M 2） | 1.00 | 2 / 4 | M′ の勝ち |
| 副: R 対 M | 下がっていない（R 2 / M 2） | 1.00 | 4 / 4 | R の勝ち |
| 副: R′ 対 M′ | 下がっていない（R′ 1 / M′ 1） | 1.00 | 4 / 4 | R′ の勝ち |

歯止めの「失敗」は、段階1の最後の段の隠しテストの失敗。内部の表現を固定するテスト（hcl の `TestParse` など）を除くと、R′ だけが 0 になる。

主な比較と M′ 対 M は、判定が付いた課題が2つだけで、どちらも同じ側が勝ったので、95% 区間は1点に潰れている。勝ち負けは傾向として読む。

## 実験の運用で起きたこと

| 起きたこと | 対応 |
| --- | --- |
| 最初の版（N、M、R の3群）の run が、どれもエージェントの起動前に止まった。ホストの Go が課題の版より新しくなり、ツールチェーンの切り替えが `GOSUMDB=off` で拒まれた | 課題の版の Go をモジュールキャッシュから直接使うようにした。同時に、群を 2×2 に組み直した。どちらも、結果が1つも出る前に行った |
| **hcl の M′ の3段目で、エージェントがコードを書く前に止まった。** declscope 0.24.2 の skill が「持ち主に namespace の指定を提案し、返事を待つ。答える人がいなければ手を付けずに残す」と書いていた。ハーネスには答える役がいなかった | traefik の R から、すべての群に「質問に答える人はいない。持ち主の判断が要る場面では、自分が勧める案で進める」という一文を足した。止まった run を探し、hcl の M′ だけをこの一文ありでやり直した。declscope 側も直し、0.24.3 で「答える人がいなければ、勧める案を実行してレポートに書く」にした（[mpyw/declscope#365](https://github.com/mpyw/declscope/pull/365)） |
| 監査の誤検知が3種類あった。`mktemp -d` が返す `/var/folders/…` を外のパスと見た。文書のリンクを直す `sed` の中の `](../../…)` を、外へのパスと見た。`grep` の検索語の中の `curl` を、ネットワークの操作と見た | 監査を直し、全 run を監査し直した。違反は残っていない |
| 「検査が役に立ったか」を、最後の検査の出力で決めていた。hcl の M′ では、最後の検査が試し打ち（名前を足して報告を確かめ、元に戻す）だった | 指摘のあとに一度でも指摘のない検査があれば「役に立った」とした。コードに指摘が残ったかは、`compliance.py` がコードそのものに聞く |
| 判定役は、`judge.json` に判定済みの組を飛ばす作りだった。hcl の M′ をやり直したあと、古い判定が使い回された | M′ が入る組だけを消して、判定し直した |
| github-mcp-server の構造レビューの途中で、使用量の上限に当たった | ハーネスが15分ごとにやり直し、上限が戻ったあとに終えた |

## 限界

| 限界 | 影響 |
| --- | --- |
| 課題が4つで、各群1回 | 判定ルールの勝ち負けは、主な比較では2課題でしか付いていない。数字は傾向として読む |
| 「答える人はいない」の一文が、同じ課題の群のあいだでそろっていない | jaeger の4群、hcl の M、R、R′、traefik の M と M′ には、この一文がない。hcl の M′（やり直し）、traefik の R と R′、github-mcp-server の4群にはある。この一文が効くのは、エージェントが質問で止まる場面だけで、ほかの run では止まった段がなかった |
| 判定役が、差の小さい組で並べた順番に引きずられた | hcl の R′ 対 R と M′ 対 M では、2回とも同じ位置のほうを選んだ。引き分けの多くは、この偏りによる |
| R′ にだけ、既存の宣言を動かしにくくする条件が入っていた | 「export された API を変えない」は、命名のルールが export された名前にも効く R′ にだけ制約になった。baseline のキーが変わる手間も R′ にだけかかる。主な比較は、この不利を含んだ結果になる。R′ だけ `exported: false` にして traefik と github-mcp-server をやり直すと、確かめられる |
| 判定役が見るのは「分割の良さ」で、declscope のルールではない | ルールを守ること（境界、命名）と、判定役の言う良い分割は、別のものとして測られた。R は判定役に好まれたが、ルールからは最も離れた |
| 既存の package に機能を足す課題だけ | 構造の大半は seed で決まっている。declscope が最初から形を決められる、新しく立ち上げる package では測っていない |
| 判定役と測られるエージェントが同じモデル | 実験1と同じ |

## 次の実験

既存の package では、declscope が分割を良くする余地が小さかった。リファクタリングさせるときは、かえって組み直しを控えさせた。次は、新しく立ち上げる package の、最初の PR から続く 5〜8本の連続で測るのがよい。baseline が要らず、declscope が最初から置き場所と境界を決められる。段を重ねたときの崩れ方（ファイルの肥大化、ファイルをまたぐ参照の数）もあわせて測る。
