# 実験2の設計

## 問い

declscope を入れたエージェントに、既存のコードをどこまで変えさせるのがよいか？

実験1では、declscope の効果がパッケージの既存の流儀で向きを変えた。機能ごとにファイルを分けたパッケージ（jaeger、github-mcp-server）では分割が良くなり、層ごとや種類ごとに分けたパッケージ（hcl、traefik）では悪くなった。hcl では、G 群が命名のルールに合わせて `ast_` の接頭辞を外し、パッケージの流儀を崩した（[実験1の報告](../1/REPORT.md)）。

declscope 0.24.2 の `declscope-authoring` は、baseline のあるパッケージでの振る舞いを、頼まれた内容で分けた。

| 頼まれた内容 | skill が求めること |
| --- | --- |
| 機能を足す、バグを直す | パッケージの既存の流儀に合わせる。既存のファイル名や baseline にある名前は変えない |
| リファクタリング | 頼まれた範囲の中では、skill の慣習に従う。範囲の外は流儀のまま |

実験2は、この2つの使い方を比べる。

| 問い | 比べる群 |
| --- | --- |
| 流儀を崩さずにルールを守らせると、分割は良くなるか | N 対 M |
| リファクタリングを頼むと、最小限の対応より分割が良くなるか | M 対 R |
| リファクタリングまで頼むと、指示なしより分割が良くなるか | N 対 R |

## 群

| | N: 指示なし | M: 最小限＋declscope | R: リファクタリング＋declscope |
| --- | --- | --- | --- |
| 課題文 | あり | あり | あり |
| 自己レビュー手順 | あり | あり | あり |
| declscope 0.24.2 と baseline、skill | なし | あり | あり |
| declscope の案内（[guardrail.md](harness/prompts/guardrail.md)） | なし | あり | あり |
| 変更の範囲 | 書かない | 課題に必要な範囲だけ（[scope-minimal.md](harness/prompts/scope-minimal.md)） | 課題の package のリファクタリングを頼む（[scope-refactor.md](harness/prompts/scope-refactor.md)） |
| 終える前のチェック | `go vet`、`go test` | N に加えて `declscope`、`declscope shrink` | M と同じ |

M と R の違いは、変更の範囲の1段落だけにする。文言の決めごとは [prompts/README.md](harness/prompts/README.md) にある。

N の条件は、実験1の A 群と同じ。それでも実験1の A の結果は使わず、N をもう一度実行する。M と R と同じ日に、同じハーネスとモデルで比べるため。

## 実験1から変えたもの

| 変えたもの | 内容 | 理由 |
| --- | --- | --- |
| 群 | A、P、G から N、M、R にした | 問いが変わったため |
| declscope | 0.24.1 から 0.24.2 にした。`~/ws-tools/declscope-0.24.2/` に固定し、実行のたびに版を確かめる | 0.24.2 の skill が、機能追加とリファクタリングで振る舞いを分けた。比べたいのはこの skill の使い方 |
| 置き場所のルール（`rule.md`） | 渡さない | 実験1では、declscope を使わない P 群にルールを伝えるために要った。実験2では M と R が skill で読む |
| 段のあいだの package の中の変更 | 3-way merge で当て、当たらなければ説明を課題文に足す | `task.yaml` に書いてあったのに、実験1のハーネスはこれを当てていなかった。traefik の2段目の隠しテストは、そのせいで3群とも落ちた |
| 課題 | 実験1で実行した4本（jaeger、hcl、traefik、github-mcp-server） | 実験1と比べやすくするため。go-sdk は実験1でも実行していない |

## 判定ルール

実験1の判定ルール（[実験1の「判定ルール」](../1/design.md#判定ルール)）を、そのまま3つの組に当てる。

| 数字 | 役割 | 決め方 |
| --- | --- | --- |
| 分割の勝率（判定役による見比べ） | 主な数字 | 課題ごとに勝率を出し、その平均の 95% ブートストラップ区間が 0.5 を上回れば勝ち、下回れば負け |
| 段階1の最後の段の失敗 | 歯止め | 失敗が相手より2回以上多ければ、勝率にかかわらず負け |
| 段階2のトークン数 | 2番目の数字 | 結論は変えない。分割が良いと次の変更も楽になるかを見る |

各群を課題ごとに1回実行する。比べた組が「差なし」のときは、実験1と同じく、各群2回ずつ一度だけ足してよい。

| 結果 | 読み方 |
| --- | --- |
| N < M、M < R | 最小限でも効き、リファクタリングを頼むとさらに良くなる |
| N < M、M ≈ R | 最小限で十分。リファクタリングを頼む意味は見えない |
| N ≈ M、M < R | ルールを守るだけでは足りない。構造を直させて初めて効く |
| M > R | リファクタリングを頼むと、かえって分割が悪くなる |

> [!IMPORTANT]
> R は既存のコードを動かすので、名前合わせ役の仕事が増え、内部の表現を固定するテスト（`white_box_tests`）に落ちやすい。歯止めはそれも含めて数える。参考として、内部の表現を固定するテストを除いた失敗も、実験1と同じく表に出す。

## 人による確かめ

実験1と同じやり方で、同僚が8組をブラインドで判定する。8組は、どの run よりも前に乱数の種を固定して選んだ（[analysis/human/pairs.json](analysis/human/pairs.json)）。並び順の秘密は git に入れていない。人と判定役の一致率が 75% に届かなければ、人が判定した組だけで結論を出す。

## 規模

4課題 × 3群 × 1回。連続が3〜5段なので、エージェントの実行は約50回になる。これに名前合わせ役、判定役、構造レビューの実行が加わる。実験1では、1回の run（3段）で約200万トークンを使った。

## 構成

パスは `experiments/2/` からのもの。課題は、リポジトリのトップの `tasks/` を実験1と共通で使う。

| パス | 中身 |
| --- | --- |
| `harness/` | 実験1のハーネスを写して、群と declscope の版を変えたもの |
| `harness/prompts/` | 各群のプロンプト |
| `runs/<task>/<arm>/<n>/` | 段ごとの差分、名前合わせの差分、`metrics.json`、gzip したトランスクリプト |
| `analysis/` | 集計スクリプトと結果の表 |
| `analysis/human/pairs.json` | 人が判定する8組 |
