# 実験2の設計

## 問い

declscope は、エージェントにどう使わせると役に立つか？ 既存のコードには手を付けず最小限の対応をさせるときと、リファクタリングまでさせるときとで、効果が違うか？

実験1では、declscope の効果がパッケージの既存の流儀で向きを変えた。機能ごとにファイルを分けたパッケージ（jaeger、github-mcp-server）では分割が良くなり、層ごとや種類ごとに分けたパッケージ（hcl、traefik）では悪くなった。hcl では、declscope を使った群が命名のルールに合わせて `ast_` の接頭辞を外し、パッケージの流儀を崩した（[実験1の報告](../1/REPORT.md)）。最小限の対応では、declscope はあまり役に立たない見込みがある。

declscope 0.24.2 の `declscope-authoring` は、baseline のあるパッケージでの振る舞いを、頼まれた内容で分けた。

| 頼まれた内容 | skill が求めること |
| --- | --- |
| 機能を足す、バグを直す | パッケージの既存の流儀に合わせる。既存のファイル名や baseline にある名前は変えない |
| リファクタリング | 頼まれた範囲の中では、skill の慣習に従う。範囲の外は流儀のまま |

実験2は、変更の範囲と declscope の有無を掛け合わせた 2×2 で比べる。

## 群

| | declscope なし | declscope あり |
| --- | --- | --- |
| 最小限の対応だけ | M | M′ |
| リファクタリングしてよい | R | R′ |

コードやディレクトリ名では、M′ を `MD`、R′ を `RD` と書く（D は declscope）。

| | M | M′ | R | R′ |
| --- | --- | --- | --- | --- |
| 課題文 | あり | あり | あり | あり |
| 自己レビュー手順 | あり | あり | あり | あり |
| 変更の範囲 | 課題に必要な範囲だけ（[scope-minimal.md](harness/prompts/scope-minimal.md)） | M と同じ | 課題の package のリファクタリングを頼む（[scope-refactor.md](harness/prompts/scope-refactor.md)） | R と同じ |
| declscope 0.24.2 と baseline、skill | なし | あり | なし | あり |
| declscope の案内（[guardrail.md](harness/prompts/guardrail.md)） | なし | あり | なし | あり |
| 終える前のチェック | `go vet`、`go test` | M に加えて `declscope`、`declscope shrink` | M と同じ | M′ と同じ |

> [!IMPORTANT]
> **変更の範囲の段落は、declscope のあり・なしで一字一句同じにする。** declscope は、案内と skill だけでエージェントに届く。範囲の段落に skill の名前やルールを書くと、R と R′ の差に文言の違いが混ざる。

文言の決めごとは [prompts/README.md](harness/prompts/README.md) にある。

## 比べる組

判定役が見比べるのは、1つの条件だけが違う4組。対角の組（M 対 R′、R 対 M′）は2つの条件が同時に違うので、見比べない。

| 組 | わかること | 扱い |
| --- | --- | --- |
| **R′ 対 R** | リファクタリングさせるとき、declscope が役に立つか | **主な比較。結論はこれで出す** |
| M′ 対 M | 最小限の対応のとき、declscope が役に立つか | 副次 |
| R 対 M | ツールなしで、リファクタリングを頼むだけで分割が良くなるか | 副次 |
| R′ 対 M′ | declscope があるとき、リファクタリングを頼むと差が出るか | 副次 |

| 結果 | 読み方 |
| --- | --- |
| R′ > R、M′ ≈ M | declscope は、リファクタリングさせるときに効く。最小限の対応では効かない |
| R′ > R、M′ > M | declscope は、どちらの使い方でも効く |
| R′ ≈ R | リファクタリングさせても、declscope を足す意味は見えない |
| R > M、R′ ≈ R | 効いているのは、リファクタリングを頼むこと自体 |

## 検査が役に立ったか

M′ と R′ では、declscope の検査（決定論的な Lint）が役に立ったかも記録する。エージェントには何も尋ねず、段階1の各段のトランスクリプトから、エージェントが実行した `declscope` と `declscope shrink` の出力を読む（`analysis/guardrail_use.py`）。

| 判定 | 意味 |
| --- | --- |
| 役に立った | 検査が指摘を出し、最後の検査では指摘がなかった。エージェントが指摘を受けてコードを直した |
| 指摘が残った | 最後の検査にも指摘があった |
| 指摘なし | どの検査も指摘を出さなかった。検査が拾うものがなかった |
| 実行しなかった | エージェントが検査を実行しなかった |

あわせて、検査の回数、出た指摘の種類（境界、命名など）、足したディレクティブと ignore の数を段ごとに残す。declscope が読み込めなかった package の型エラーは、指摘に数えない。

これは判定ルールには入れない、探索的な記録。検査がなかったらコードがどうなっていたかは、トランスクリプトからは分からない。それは M と M′、R と R′ の比べ（分割の見比べと `analysis/compliance.py`）が答える。

## 判定ルール

実験1の判定ルール（[実験1の「判定ルール」](../1/design.md#判定ルール)）を、上の4組に当てる。結論は主な比較（R′ 対 R）で出す。

| 数字 | 役割 | 決め方 |
| --- | --- | --- |
| 分割の勝率（判定役による見比べ） | 主な数字 | 課題ごとに勝率を出し、その平均の 95% ブートストラップ区間が 0.5 を上回れば勝ち、下回れば負け |
| 段階1の最後の段の失敗 | 歯止め | 失敗が相手より2回以上多ければ、勝率にかかわらず負け |
| 段階2のトークン数 | 2番目の数字 | 結論は変えない。分割が良いと次の変更も楽になるかを見る |

各群を課題ごとに1回実行する。主な比較が「差なし」のときは、実験1と同じく、R と R′ を2回ずつ一度だけ足してよい。

> [!IMPORTANT]
> R と R′ は既存のコードを動かすので、名前合わせ役の仕事が増え、内部の表現を固定するテスト（`white_box_tests`）に落ちやすい。歯止めはそれも含めて数える。参考として、内部の表現を固定するテストを除いた失敗も、実験1と同じく表に出す。

## 人による確かめ

実験1と同じやり方で、同僚が8組をブラインドで判定する。8組は、どの run よりも前に乱数の種を固定して選んだ。4組それぞれから2課題ずつ（[analysis/human/pairs.json](analysis/human/pairs.json)）。並び順の秘密は git に入れていない。人と判定役の一致率が 75% に届かなければ、人が判定した組だけで結論を出す。

## 規模

4課題 × 4群 × 1回 = 16回の run。連続が3〜5段なので、エージェントの実行は約60回になる。これに名前合わせ役、判定役、構造レビューの実行が加わる。実験1では、1回の run（3段）で約200万トークンを使った。

## 構成

パスは `experiments/2/` からのもの。課題は、リポジトリのトップの `tasks/` を実験1と共通で使う。

| パス | 中身 |
| --- | --- |
| `harness/` | 実験1のハーネスを写して、群と declscope の版を変えたもの |
| `harness/prompts/` | 各群のプロンプト |
| `runs/<task>/<arm>/<n>/` | 段ごとの差分、名前合わせの差分、`metrics.json`、gzip したトランスクリプト。`<arm>` は `M`、`MD`、`R`、`RD` |
| `analysis/` | 集計スクリプトと結果の表 |
| `analysis/human/pairs.json` | 人が判定する8組 |
